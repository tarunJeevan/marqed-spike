N1/N2 make no difference here — evidence: test `typing_a_heading_follows_c4_at_every_key_under_every_policy`.
- F-39 (T8): typing `**important**`: no marker is concealed until the 12th key. `**important*` parses as a literal `*` followed by an emphasis `*important*` (range 1..12), and the bar at its end is not strictly inside it, so the emphasis markers are concealed at once and one of the visible `*` disappears (`**important` becomes `*important`). The 13th key makes a strong (0..13), concealed with the bar at its end, so the text becomes `important`. Moving the bar left one or two positions puts it strictly inside and reveals `**important**`. - F-40 (T8): Backspace into a concealed marker. With the bar right after a concealed closing `**` (`**b**|`, shown as `b`), Backspace deletes the hidden final `*` ("regardless of concealment", C-9), so the strong is gone but the display changes only from `b` to `*b` (a literal `*` plus an emphasis `*b*` with its markers still concealed); a second Backspace leaves `**b` and everything is plain source. - F-43 (T9): L's failures have one cause. C-10 describes L as position, then kind, then hash, but the old and new ranges are in different coordinate systems; any edit that changes the length shifts every later block by the edit's delta, and a block keeps its id only while its new range still overlaps its old one, so the larger the shift relative to the block, the more ids are lost. Case 4 (a seven-byte edit) already renumbers the tail. Over 2000 seeded single random edits on generated documents, L lost the id of a block in an untouched common prefix or suffix in 631 (32%) and never crossed an order; C had no violation in the same 2000 and in 1000 random edit chains. - F-45 (T9): neither strategy detects a move. Swapping `alpha` and `beta`: C anchors on `beta` by content (it keeps its id) and `alpha` gets a fresh one; L gives each position's id to whatever now sits there. A moved block therefore loses its id under C (its old id is retired) and takes over another block's id under L. ## Halts
- H3 @ T6 (2026-10-18): T6.md asks that "every visible boundary round-trips `vis → point → vis`". That is unachievable for boundaries inside whitespace that cosmic-text collapses at a soft wrap, because several boundaries share one pixel position and `Buffer::hit` (the mechanism C-8 prescribes for `point → (visible byte, affinity)`) can only return glyph starts and ends. It is a conflict between the T6 task file and what C-8 can deliver, and making it pass would mean weakening the property (H5), which I will not do, and the property lives in `docs/tasks/T6.md`, which I may not edit. Minimal counterexample: visible text `" **word aaa"` (source `" **word aaa"`, cursor away, all markers concealed) laid out at width 50: boundary 0 locates at `(row 0, x 0.0)`, and `hit` at that point returns byte 1, because the leading space has no glyph and the first glyph starts at byte 1. Second shape (116 of the 137 enumerated failures; I did not extract a minimal example): several consecutive swallowed spaces at a row end collapse to one x, and `hit` returns the first of them. (A single swallowed space at a wrap, e.g. `"👍🏽aword aa**word "` at width 120, was also failing at first and is fixed by the hanging-whitespace model.) Everything else holds: the strict property passes on the fixtures and hand-built paragraphs, and over 104,174 random boundaries all 137 failures are coincident-position whitespace (F-23, F-24). The developer must decide how to restate the property.
